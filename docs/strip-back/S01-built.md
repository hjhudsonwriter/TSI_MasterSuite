# S01 built: the version 4 shell and the safety net

Step S01 of the Strip Back Overhaul (`docs/STRIP-BACK-PLAN.md`; design in `docs/strip-back/J-cross-cutting.md` sections 0 to 4 and 8.1). No facility is removed yet: this is the shell every later step adds to.

## What was built

- **A new Bastion is version 4** (`R.defaultState`, `R.STATE_VERSION`). `R.migrateToV3` is unchanged except that it now leaves a version 3 *or newer* save alone (`s.v >= 3`, was `=== 3`), so it can never run on a version 4 save.
- **`tools/bastion/strip-back-rules.js`** (new, loaded straight after `rules.js` in the Bastion, Explorer and Beast Handler manifests in `shared/data/tools.js` and in `tests/rules.html`). It depends only on `rules.js`. It holds:
  - the ordered registry `R.stripBackSteps` (two steps today: `sweepFacilities`, the catch-all, and `finish`);
  - `R.migrateToV4(raw, data)` → `{ save, report, before }` (pure: no storage, clock or dice; never touches the object it is given; a version 2 save goes through `R.migrateToV3` first and the report keeps its lines);
  - `R.needsStripBack(s, data)` (version below 4, or any step's `detect` finds something) and `R.stripBackLeftovers`;
  - the shared helpers every step uses: `R.stripBackCancel` (cancel an order and give back its gold, Favour and goods, once), `R.stripBackMoveOrder`, `R.stripBackPayGold`, `R.stripBackSay`, `R.stripBackName`;
  - `R.stripBackAudit(before, after, report[, data])`: the seven guarantees I1 to I7 of J 4.5 (it also checks each cancelled order's gold, Favour and goods against the order in `before`);
  - the words: `R.stripBackHeadline`, `R.stripBackText`, `R.STRIP_BACK_NOTE`, `R.STRIP_BACK_HEADINGS`.
- **`R.fromSave`** converts anything that `R.needsStripBack` (in memory only), so the Beast Handler on the laptop gets a clean view without writing. A version 4 save that an older copy of the suite overwrote (it holds a facility the Bastion does not know) is converted again, with a short notice (`again: true`).
- **`bastion-data.js` `stripBack`** = `{ facilities, orders, names, menagerieValue }`. `facilities` holds the 13 retiring facilities' names (checked against the catalogue by a test); the other three are empty, for the later steps.
- **`shared/js/campaign-rules.js`**: `inDaysSave` accepts 2, 3 or 4; `TSI.campaign.RETIRED_FACILITIES` (the 13 ids); `summary` and `bastionComing` leave out the pending orders of those facilities for a save below version 4 (a version 4 save is never filtered). The Explorer, `shared/js/bridge-rules.js`, `shared/js/dmdoc.js` and the Beast Handler were checked: none of them gates on the version.
- **`TSI.store.keepCopy(key, reason)`** (`shared/js/store.js`, pure parts `uniqueKey` and `copyNote` in `store-rules.js`): copies a record under `tsi.quarantine.<tool>.<name>.<stamp>` and leaves the live key alone. `quarantine` now shares `uniqueKey`.
- **`tools/bastion/tool.js`**: copy first (`keepCopy`), then the converted save is written at the end of start-up (it cannot be saved without its copy: same queue, same transaction or later). If the audit fails, nothing is written or set aside and a small page says "The Bastion couldn't be converted safely. Nothing has been changed." with "Download my Bastion as a file" (the raw record) and the list of what the check found. The 30-second corner notice is replaced by a box that stays until "I've read this" (`migration.v4.shown` is set, and saved, only then; Esc closes it without marking it read, so a reload shows it again). "Save this as a text file" uses `TSI.download`. A one-line version ("The Bastion has been updated; nothing of yours changed.") shows when nothing was converted. Management has a "What changed" row that opens the same text. `ns.debug.changes`, `showChanges` and `sweepOrphans` are for the tests.
- **Fixtures**: `tests/fixtures/make-heavy.js` makes `bastion-v3-heavy.json` (28 pending orders, one for at least every row of J 4.3) and `bastion-fixtures.js` (every `bastion-*.json` as a script, because `tests/rules.html` cannot read `.json` from a file). `tests/fixtures/README.md` added.
- **Tests**: `tests/rules/strip-back.test.js` (31 tests), more in `campaign.test.js` and `store-rules.test.js`; `tests/e2e/migration-v4.test.js` (22 checks); a live `keepCopy` check in `phase1.test.js`; `H.ackChanges` in `tests/e2e/helpers.js` (and `H.dismissNotices` presses "I've read this" if the box is up).

## Deviations from the brief, and judgement calls

1. **The orphan-key sweep is switched off while the War Table is part of the Bastion.** The brief says to move `tsi.bastion.warMap`, `.warTable` and `.warTerrain` to quarantine every time the Bastion opens. At S01 the War Table still uses them (war removal is S06), so moving them now would take a working feature's saved battle map away on every open. The sweep (`sweepOrphans` in `tool.js`, pure list `R.STRIP_BACK_ORPHAN_KEYS`) is therefore guarded by `if (!ns.warTable)`: the step that deletes `war-table.js` turns it on with no other change. It is tested by forcing it (`ns.debug.sweepOrphans(true)`). `R.importProblem` already ignores the three keys, as asked.
2. **The corner notice for version 3 is kept** for a version 2 save (phase9 expects it), so a version 2 file shows that notice *and* the new box, which holds the earlier change's lines too (heading "Facilities (the change of 13 October 2026)").
3. **While the box is waiting, nothing moves on**: the Bastion does not read the Explorer's day or pass days, apply DM doc edits or Beast Handler requests, or offer a crest (`changesOpen` guard in `tool.js`). Otherwise a day could pass, with dice boxes, underneath a report that describes the Bastion as it was converted. The cost: tests that open a version 2 or 3 save must press "I've read this" before waiting for the Bastion to anchor to the Explorer's day (`H.ackChanges`).
4. **The registry's order**: later steps go **above** `sweepFacilities`, which is the catch-all for anything left over (a facility the catalogue does not know). `war_council` and `trade_network` are not catalogue facilities but their orders are real until their steps remove them, so the catch-all leaves them alone (`R.STRIP_BACK_PSEUDO_FACILITIES`).
5. **`migrateToV4` returns `{ save, report, before }`**, not just `{ save, report }`: the audit needs what the new steps started from (after the earlier version 3 step for a version 2 save).
6. **No Day Log line is written by the conversion** (the old version 3 step wrote one using the clock; this one is pure). The report is kept in `migration.v4` and readable from Management.
7. **The audit's idempotence check (I7) runs every step again on a copy**, not only `migrateToV4`, because a clean save is not converted at all and that alone would prove nothing.
8. **Goods rows the conversion makes get a fixed id** (`returned-<good>`), never a random one, so converting the same save twice gives the same result.
9. **A new test file is wired into the rules page**; `tests/rules.html` also loads `tests/fixtures/bastion-fixtures.js`.
10. **Expectations of older tests changed on purpose**: a new Bastion and a converted version 2 save are version 4 (`bastion.test.js`, `phase9.test.js`); the two import checks for the War Table's saves now expect them to be ignored (`bastion.test.js`, `bastion-campaign.test.js`).
11. **Not done**: the Day Log text-file offer (J 4.6) is S18; the final settlement of the Hall, the war, the rest of the facilities and every other step are later steps.
