# S01 built: the version 4 shell and the safety net

Step S01 of the Strip Back Overhaul (`docs/STRIP-BACK-PLAN.md`; design in `docs/strip-back/J-cross-cutting.md` sections 0 to 4 and 8.1). No facility is removed yet: this is the shell every later step adds to.

## What was built

- **A new Bastion is version 4** (`R.defaultState`, `R.STATE_VERSION`). `R.migrateToV3` is unchanged except that it now leaves a version 3 *or newer* save alone (`s.v >= 3`, was `=== 3`), so it can never run on a version 4 save.
- **`tools/bastion/strip-back-rules.js`** (new, loaded straight after `rules.js` in the Bastion, Explorer and Beast Handler manifests in `shared/data/tools.js` and in `tests/rules.html`). It depends only on `rules.js`. It holds:
  - the ordered registry `R.stripBackSteps` (two steps today: `sweepFacilities`, the catch-all, and `finish`);
  - `R.migrateToV4(raw, data)` → `{ save, report, before }` (pure: no storage, clock or dice; never touches the object it is given; a version 2 save goes through `R.migrateToV3` first and the report keeps its lines);
  - `R.needsStripBack(s, data)` (version below 4, or any step's `detect` finds something) and `R.stripBackLeftovers`;
  - the shared helpers every step uses: `R.stripBackCancel` (cancel an order and give back its gold, Favour and goods, once), `R.stripBackMoveOrder`, `R.stripBackPayGold`, `R.stripBackSay`, `R.stripBackName`;
  - `R.stripBackAudit(before, after, report[, data])`: the seven guarantees I1 to I7 of J 4.5. It also checks every order against the order in `before`: a **cancelled** order's gold, Favour (handed back, or said to have no god: `favourUnplaced`) and goods; a **kept** order must be identical; a **moved** order must have the same `costGP`, `favourCost`, `inputs`, `issuedDay` and `dueDay`, and may differ only in `R.STRIP_BACK_MOVE_KEYS` (`facId`, `fnId`, `label`, `optionLabel`, `chosen`, `notes`: its place, name and choice). `R.stripBackMoveOrder` refuses any other key (it throws, so the conversion fails closed) and an order with no id;
  - the words: `R.stripBackHeadline`, `R.stripBackText`, `R.STRIP_BACK_NOTE`, `R.STRIP_BACK_HEADINGS`. The stored lines are worded as of the day they happened ("on Day 12 it went from 2,000 gp to 2,120 gp"), never "it is now", because Management > What changed reads them again after play; the live balance is shown only in the first-open box (computed from the real treasury);
  - `R.stripBackReportRecord(prev, report, summary)`: what `finish` keeps in `migration.v4`. A report that has not been read (`shown` is not true) is **never replaced**: a second conversion adds its lines after the earlier ones ("More was found on Day N and put right the same way."), keeps the first day and adds the gold totals, and does not blame an older copy of the suite. "An older copy of the suite had saved over your Bastion" (`again: true`) is said only when the earlier report had been read and something then reappeared.
- **`R.fromSave`** converts anything that `R.needsStripBack` (in memory only), so the Beast Handler on the laptop gets a clean view without writing. A version 4 save that an older copy of the suite overwrote (it holds a facility the Bastion does not know) is converted again, with a short notice (`again: true`).
- **`bastion-data.js` `stripBack`** = `{ facilities, orders, names, menagerieValue }`. `facilities` holds the 13 retiring facilities' names (checked against the catalogue by a test); the other three are empty, for the later steps.
- **`shared/js/campaign-rules.js`**: `inDaysSave` accepts 2, 3 or 4; `TSI.campaign.RETIRED_FACILITIES` is ONE table, `{ facility id: 'cancel' | 'move' }`, for the 13 retiring facilities (`'cancel'`: the Barracks, Armoury, Watchtower, War Room and Menagerie; `'move'`: the Library, Arcane Laboratory, the three Shrines and the three beast buildings). `TSI.campaign.cancelledByConversion(order)` says whether the conversion will CANCEL an order (a `'cancel'` facility, any Upgrade order at a retiring facility, the Shrine orders that end, a beast building's training/riding/flight orders). `summary` and `bastionComing` leave out only those, for a save below version 4: an order the conversion merely MOVES (a House order to the Beast Pen, a Library or Laboratory job to the Workshop, the Favour prayer to the Temple) is still forecast, on its own due day (a version 4 save is never filtered). **Later steps must keep this table true**: when a step retires or re-homes a facility, change its row (and `cancelledByConversion`) in the same commit as its step in `strip-back-rules.js`; `tests/rules/campaign.test.js` has a test for each kind. The Explorer, `shared/js/bridge-rules.js`, `shared/js/dmdoc.js` and the Beast Handler were checked: none of them gates on the version.
- **`TSI.store.keepCopy(key, reason)`** (`shared/js/store.js`, pure parts `uniqueKey`, `copyNote` and `copyIsIntact` in `store-rules.js`): copies a record under `tsi.quarantine.<tool>.<name>.<stamp>` and leaves the live key alone. `quarantine` shares `uniqueKey`. **It tells the truth**: it writes the copy on its own (after any save already going, outside the shared queue, so another save failing cannot fail it and one in flight cannot make it succeed early), then READS IT BACK from the browser and compares it; it resolves with the copy's key only then, else `null` with the reason in `TSI.store.copyProblem()` and nothing left behind. In a browser that keeps no saves (memory only) it always gives `null`: it never claims a copy that would vanish.
- **`tools/bastion/tool.js`**: the conversion FAILS CLOSED, in this order. (1) It is converted in memory and checked (`R.stripBackAudit`; an error thrown by a step counts as failing the check). (2) The Bastion as it was is copied beside the live one (`keepCopy`, so it is in Back up everything and the live save is never absent), and `start` waits until the copy is confirmed saved and read back. (3) Only then does the Bastion open: the converted save is drawn, written, and the box opens after that. If the check fails, or the copy cannot be confirmed (storage full, or memory-only mode), nothing is written, nothing is set aside, nothing is marked converted, and a small page says "The Bastion couldn't be converted safely. Nothing has been changed." with "Download my Bastion as a file" (the raw record) and the reason (for a memory-only browser it says plainly that no copy can be kept). The box that stays until "I've read this" (`migration.v4.shown` is set, and saved, only then; Esc closes it without marking it read, so a reload shows it again) opens only after the first successful render and save of the converted Bastion (a later start-up error never leaves it over the "couldn't open" page); if that save fails, a notice says so instead. The War Table's leftover saves are set aside only after the audit passed and the converted save and its copy are safely written (still behind `if (!ns.warTable)`). "Save this as a text file" uses `TSI.download`. A one-line version ("The Bastion has been updated; nothing of yours changed.") shows when nothing was converted. Management has a "What changed" row that opens the same text. `ns.debug.changes`, `showChanges` and `sweepOrphans` are for the tests.
- **Fixtures**: `tests/fixtures/make-heavy.js` makes `bastion-v3-heavy.json` (28 pending orders, one for at least every row of J 4.3) and `bastion-fixtures.js` (every `bastion-*.json` as a script, because `tests/rules.html` cannot read `.json` from a file). `tests/fixtures/README.md` added.
- **Tests**: `tests/rules/strip-back.test.js` (every guarantee has a test that INJECTS the fault: zeroed goods, a dropped Favour cost, a changed due day, a changed order the report does not mention, an under-refund of gold, goods or Favour for a cancelled order), more in `campaign.test.js` and `store-rules.test.js`; `tests/e2e/migration-v4.test.js` (a quota-limited plain-storage stand-in, a memory-only browser, a failing check and a start-up that fails part-way, all of which must change nothing); live `keepCopy` checks in `phase1.test.js` (including a save in flight and another save failing); `H.ackChanges` in `tests/e2e/helpers.js` (and `H.dismissNotices` presses "I've read this" if the box is up).

## Deviations from the brief, and judgement calls

1. **The orphan-key sweep is switched off while the War Table is part of the Bastion.** The brief says to move `tsi.bastion.warMap`, `.warTable` and `.warTerrain` to quarantine every time the Bastion opens. At S01 the War Table still uses them (war removal is S06), so moving them now would take a working feature's saved battle map away on every open. The sweep (`sweepOrphans` in `tool.js`, pure list `R.STRIP_BACK_ORPHAN_KEYS`) is therefore guarded by `if (!ns.warTable)`: the step that deletes `war-table.js` turns it on with no other change. It runs only after the audit passed and the converted save is written, so the "nothing has been set aside" page is always true. It is tested by forcing it (`ns.debug.sweepOrphans(true)`). `R.importProblem` already ignores the three keys, as asked.
2. **The corner notice for version 3 is kept** for a version 2 save (phase9 expects it), so a version 2 file shows that notice *and* the new box, which holds the earlier change's lines too (heading "Facilities (the change of 13 October 2026)").
3. **While the box is waiting, nothing moves on**: the Bastion does not read the Explorer's day or pass days, apply DM doc edits or Beast Handler requests, or offer a crest (`changesOpen` guard in `tool.js`). Otherwise a day could pass, with dice boxes, underneath a report that describes the Bastion as it was converted. The cost: tests that open a version 2 or 3 save must press "I've read this" before waiting for the Bastion to anchor to the Explorer's day (`H.ackChanges`).
4. **The registry's order**: later steps go **above** `sweepFacilities`, which is the catch-all for anything left over (a facility the catalogue does not know). `war_council` and `trade_network` are not catalogue facilities but their orders are real until their steps remove them, so the catch-all leaves them alone (`R.STRIP_BACK_PSEUDO_FACILITIES`).
5. **`migrateToV4` returns `{ save, report, before }`**, not just `{ save, report }`: the audit needs what the new steps started from (after the earlier version 3 step for a version 2 save).
6. **No Day Log line is written by the conversion** (the old version 3 step wrote one using the clock; this one is pure). The report is kept in `migration.v4` and readable from Management.
7. **The audit's idempotence check (I7) runs every step again on a copy**, not only `migrateToV4`, because a clean save is not converted at all and that alone would prove nothing.
8. **Goods rows the conversion makes get a fixed id** (`returned-<good>`), never a random one, so converting the same save twice gives the same result.
9. **A new test file is wired into the rules page**; `tests/rules.html` also loads `tests/fixtures/bastion-fixtures.js`.
10. **Expectations of older tests changed on purpose**: a new Bastion and a converted version 2 save are version 4 (`bastion.test.js`, `phase9.test.js`); the two import checks for the War Table's saves now expect them to be ignored (`bastion.test.js`, `bastion-campaign.test.js`).
11. **Not done**: the Day Log text-file offer (J 4.6) is S18; the final settlement of the Hall, the war, the rest of the facilities and every other step are later steps.
12. **After the review (22 October 2026)**: the conversion was made to fail closed (see tool.js above); the audit and `R.stripBackMoveOrder` were tightened (a step that asks to change what an order paid, or its days, now stops the conversion instead of passing quietly); an unread report is merged, not replaced; the stored lines no longer say "it is now". Two judgement calls: (a) if the copy is confirmed but the converted save then cannot be written (a very full browser), the copy stays and the Bastion converts again at the next open, which makes another copy (the old Bastion is never touched, and a notice says it was not saved); (b) `notes` is in the move allow-list because the Library's Research orders carry scripture notes that the Workshop's Scholar will word again; add a key to `R.STRIP_BACK_MOVE_KEYS` only in the commit of a step that really needs it, with its test.
